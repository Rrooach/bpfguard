# SWE-bench / Terminal-Bench 非 GPU 补验结果

这轮回答两个问题：之前列出的六项缺口是否补上；补上后，在真实 benchmark 任务及其源码上能不能运行、产生可复查的数据。

结论：六项都有实现和实测，测试与证据重放通过；**观测仍有明确缺口，优先级策略也没有带来整体提速**。没有运行 GPU，没有新增付费模型请求。

## 1. 实际跑了什么

| 验证 | SWE-bench Verified | Terminal-Bench |
|---|---|---|
| 官方任务 | `psf__requests-1142`，25 次 | `html-js-filter`、`bun-sourcemap-leak`，各 25 次 |
| 官方检查器结果 | 25/25 通过 | 50/50 通过 |
| Host 独立证据重放 | 25/25 通过 | 50/50 通过 |
| 逐次搜索计时 | 40 次正式试验，2,560 次查询 | 40 次正式试验，2,560 次查询 |
| 搜索＋CPU 推理＋编译竞争 | 8 次配置调优＋25 次独立对照 | 8 次配置调优＋25 次独立对照 |

官方任务使用固定参考解，目的是保证每个诊断档位运行相同工作、用官方检查器确认工作没有做错。**这不是让模型重新解 75 道题，也不是完整题集分数。**

逐查询和混合试验使用固定任务镜像中的原始源码，但分别是搜索机制实验、CPU 资源竞争实验，不冒充自主修复任务。混合实验中的编译是固定合成负载，本地推理使用固定的小型 CPU GGUF 模型，不代表生产大模型。

## 2. 六项缺口如何处理

| 原问题 | 本轮处理与结果 |
|---|---|
| I/O 缺前值和线程计数回退被误算 | 修复分析器并增加回归测试；缺前值、缺字段、计数回退返回未知，不补零，也不输出负数“有效增量” |
| 不知道关键线程等了多久 | 独占 Guest 开启 schedstats；两套混合实验共重算 290 个有身份绑定的关键分发线程等待区间；官方任务另有 782 个完全位于执行窗口内的有效线程区间 |
| 只有整批搜索耗时 | 保存每次查询的开始、结束、耗时、实际扫描或复用、进程及任务身份；正式 5,120 次查询均从原始记录重算，另保留 1,024 次预热查询 |
| 静态基线只试一个配置 | 预声明比较 2/3 个保留 CPU × 2/4 个编译 worker；每项两次调优，冻结选择后再做独立重复测试；两套均选出 3 CPU / 4 worker，仅是所测候选中最好 |
| CPU 分配＋请求优先级缺完整对照 | 两套均完成 G0–G4 各 5 次；验证真实排队次序，同时计算重点任务、竞争任务和全部工作耗时 |
| 详细诊断开销未配对 | 每个官方任务在 baseline、threads、kernel、files、perf 五档各跑 5 次，随机化重复块，并保留逐对差值与区间 |

线程轮询不是完整线程生命周期记录：还有 205 个线程只捕获到一个样本，无法计算其等待区间；不能把它们解释为“没有等待”。

## 3. 优先级实验发现了什么

与本轮调优选出的固定 CPU 配置相比，阶段 CPU 分配＋请求优先级（G4）的五次配对结果为：

| 指标 | SWE 源码场景 | Terminal 源码场景 |
|---|---|---|
| 重点任务 A 的延迟 | 降低约 42.9% | 降低约 43.2% |
| 所有工作完成时间 | **增加约 12.5%** | **增加约 13.7%** |
| 竞争推理请求 B 的最大排队等待 | 增加约 62.9% | 增加约 64.5% |

它能让重点任务插队更快完成，但把成本转移给其他任务，整体更慢。当前证据支持“存在取舍”，**不支持“调度优化成功”**。

相同查询复用确实减少了实际扫描，但未复用和复用两种实验没有交错随机运行，时间差仅作为描述性结果。SWE 源码约 2.21 MB，Terminal 源码仅约 4 KB，不代表大仓库、冷磁盘或内存压力场景。

## 4. 额外诊断要花多少时间

以下是相对于“相同 Observer＋100 ms sampler”的任务执行耗时增幅中位数，每格 5 次配对，**不是 Observer 的总开销**：

| 任务 | 线程采样 | 线程＋全六组内核诊断 | 文件 profiler | perf |
|---|---|---|---|---|
| SWE requests | +0.12% | +6.18% | +1.87% | +1.79% |
| Terminal html | −1.32% | +19.39% | +0.71% | +1.30% |
| Terminal bun | −1.89% | +13.43% | +0.74% | +3.74% |

负数是小样本波动，不表示开启采集会加速。部分区间很宽，不能据此给生产 SLA。完整报告保留逐对数据和均值的 bootstrap 95% 区间；均值区间不是中位数区间。

所有档位都共同启用了 `schedstats=1`，这轮没有测从关闭到开启该内核统计的成本。`kernel` 比 baseline 多了线程轮询和内核探针两部分，报告另提供相对 `threads` 的比较，避免把整段差值全算作探针成本。perf 可以启动、采样并解析，但未独立证明其采样覆盖完整。

## 5. 通过了哪些检查，还有什么未知

- `make check-all` 通过：376 项 Rust、326 项 Python 测试，以及现有构建、脚本和 BPF 快路径检查。
- 75 份官方任务证据在导出后再次由固定摘要的 Host verifier 独立重放，共核对 173,451 条事件。
- 独立重放通过表示原始记录、身份绑定和重算检查通过，**不表示没有漏采**。75 份原始 Observer 证据仍保留 `INCOMPLETE`。
- Terminal 混合实验保留一次 `kh_sched_exit` recursion miss；其目标归属未知，资源解释完整性仍不足。没有删除该轮或改成零。
- 对象解析、存储队列和短线程覆盖的既有缺口仍在；有效耗时可以和不完整资源历史同时存在。
- 初始缺 g++、低 CPU 配置超时和旧报告解析错误的失败材料全部保留。最终 parser 源码与历史实际执行入口版本分开记录，不能拿最终版本反推历史执行版本。

因此准确说法是：**六项增强已在声明的小规模场景中完成实现与验证，不是“除了 GPU 一切已严格完整”。**
