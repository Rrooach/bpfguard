# 这一轮到底完成了什么

> 本文主体是 2026-10-14 的历史阶段记录，不是“除 GPU 外已全部严格验收”的声明。后续审计发现混合分析器缺失/回退计数处理、线程等待验收、逐查询计时、静态基线调优、G4 联合对照及详细诊断配对开销仍需补验。2026-10-15 的修复、真实任务试验和剩余未知分别见 [benchmark 补验说明](../agent-benchmarks/README.md#非-gpu-性能补验2026-10-15) 与新的原始结果目录 `.output/benchmark-profile-20261015/`；旧失败和旧报告不覆盖。

这轮工作的目标是：不止看到“资源很忙”，还要知道哪个 Agent 的哪个步骤变慢、有哪些证据支持这个解释，以及只改一个因素后，所有工作是否更早完成。

所有被测任务都在独立实验 QEMU 的目标 Linux 中运行。物理服务器只负责构建和离线复算，不是被测对象。代码保留在 `profile-master`；原有修改和失败记录没有撤销。

## 1. 现在能看到什么

## 2. 两个问题都跑出了可以复验的结果

### 多个 Agent 搜索同一个仓库

搜索矩阵完成 **160 轮、1280 个逻辑任务**：冷/热缓存 × 共享/独立目录 × 1/2/4/8 并发 × 是否复用等价查询，5 个随机重复块。

每轮都是 8 个任务，每个完成 8 次逻辑查询。唯一干预是复用完全相同的查询结果：实际扫描从 64 次降为 1 次，另外 63 次读取本轮缓存；首次扫描仍在计时窗口内。缓存同时绑定仓库内容、权限视图、查询参数与二进制版本。

在热缓存、共享目录、8 并发条件下，全部任务完成时间从中位 **0.232 秒降至 0.049 秒，约减少 79%**；冷缓存同条件约减少 50%。16 个条件均有支持收益的配对区间，1280 份原始输出在 Host 重算后完全一致。

这证明本场景的重复搜索可以消除大量工作；不是声称真实 Agent 的所有查询都重复，也不是文件系统创新已经成立。

内存校准另跑 **20 轮、160 个任务**。同样读取 8×320 MiB，只改变 `memory.high`，保留相同 `memory.max`。受限组同时出现 memory PSI、回收和 refault，完成时间显著增加；对照组没有这些信号。这证明采样器能识别人为制造的内存压力，不是优化收益。

### 编译和本地推理同时运行

不是远程 API，也不是用 sleep 模拟模型：使用固定版本 llama.cpp 和真实 15M GGUF CPU 模型。A 做搜索→输入准备→推理，B 完成相同的 16 个编译单元和两次推理；对照中没有少做 B。

最终轻量配置跑了 **20 轮**，每种条件 5 次；旧版本、调度诊断、开销和队列控制另存，并独立重放。

| 条件 | A 完成时间中位数 | 全部工作完成时间中位数 |
|---|---:|---:|
| A+B 默认竞争 CPU | 2.978 秒 | 2.979 秒 |
| 为 A/共享引擎静态预留两核 | 1.574 秒 | 2.557 秒 |
| 根据 A 已知阶段动态调整 CPU | 1.792 秒 | 2.597 秒 |

静态预留让 A 的配对延迟约减少 **48%**，全部工作约减少 **16%**，区间支持收益。代价也保留：B 的编译吞吐约下降 7%；算上 B 的推理，其总完成时间仍有所改善。

共享批次也补了真实校准：另外启动两 slot 引擎，让两个 Agent 的请求同时执行，实际形成 **32 个双请求批次、70 个工作线程处理区间**，并在 Host 从原始事件重新核对成员。官方 API 实际读出共享 KV 缓存的 508/510 个占用 cell（容量1024）；它是逻辑占用，不是显存字节，不会平均分摊给两个请求。这个额外校准不混入上面的性能矩阵。

**动态方案没有胜过静态预留。** 这不是删掉的失败样本：共享引擎可能在 A 搜索时处理 B，不能只看 A 的阶段就假定共享服务不需要 CPU。当前实验证实的是 CPU 干扰和静态预留的收益，不是 GPU 协同调度。

## 3. 开销不是“全部很低”

真正三组开销完成 **120 轮、960 个任务**：不启用 Observer、启用同一个 Observer、再增加 sampler；包括 50/100/500/1000 ms 的采样间隔。详细内核诊断没有混入这些常态组。

- 这个短搜索场景中，Observer 本身热路径增量约 **11%–13%**：100–1000 ms 条件约11%–12%，50 ms 对照约13%。
- 100 ms sampler 相对同一个 Observer 的增量中位约 **1%–2%**，小样本区间跨零，不能说零成本或显著加速。
- 推理高频 FORENSIC 插桩优化后仍约 **27%**，默认关闭，只用于诊断。LIGHT 减到每请求 7 条原生事件；5 个配对试验没有分辨出显著增量，但它也不声称记录每次 decode/worker。
- 准备、结束等待、快照/验证、采集器 CPU/RSS 和证据大小另存；以上热路径数字不是 VM 冷启动或开启所有状态确认器的总成本。

## 4. 反复迭代修掉了什么

不是一次跑过就停止。文件表溢出、fexit 跳过、内核 ctime 标志、共享请求关联、冷读准备次序和采样口径都经过失败→修复→实测；失败证据保留。

特别是高频 syscall 探针：旧 raw tracepoint 在当前内核上出现跳过，改用有 ABI 检查的 kprobe 后，4 个线程各运行 10 万次 `getpid()`，实际记录 **40 万次**，计量探针跳过和未配对均为零。注册用的无载荷探针单列，不冒充计量完整性。

文件校准两域各返回 800 字节，实测精确得到 1600 字节。最后搜索诊断成功关联 914 个语料文件，并发现 1053 个对象被两个域共同访问；不把返回字节说成磁盘读取量，也不把累计 VFS 时长相加成墙钟时间。

后续检查再次补了身份读取失败计数和非 x86-64 门禁，重新在 Guest 校准1600字节通过。独立热点诊断使用与原 GNU grep 完全匹配的 build-id 调试信息，不替换搜索二进制；442个样本中已能区分用户匹配函数、内核数据复制和目录查找。它是诊断候选证据，不是精确函数耗时账单。

随后进一步修复过早启用、兼容ABI别名和缺健康字段仍可标完整的问题。schema2真实正反例再次通过：校准文件正常读取1600字节，每域对该文件的一次成功映射和一次EACCES失败映射均记录、映射字节为0；兼容ABI的4次尝试明确使结果不完整，目录操作也不冒充读字节。

80份真实Observer WAL已在Host独立重放通过，主线程又单独重放了一遍；它证明证据绑定和复算通过，但这些审计完整度仍是INCOMPLETE，不会被性能试验覆盖或改绿。

## 5. 尚不能声称完成的范围

当前物理服务器没有可用于推理的 GPU，Guest 也没有 GPU 直通。因此 **GPU 排队、kernel/memcpy 时间线、显存与 GPU 调度收益尚未通过真实硬件 E2E**。GPU 导入/关联接口及测试不能代替该实验。继续这项验收需要目标 Linux 中可用的计算 GPU、驱动和 profiler。

文件 mmap 的实际访问字节、io_uring、所有短命线程的完整生命周期，以及任意共享服务的精确成本分账不在本版承诺中；未覆盖项明确保留。产品 V8 runtime 没有在本轮修改。这些边界不影响已经实测的 CPU、搜索和文件诊断结论，也不能被它们掩盖。

块设备诊断也有不可见的队列和请求生命周期：真实搜索中发现的19条旧边界告警完整保留。新增有界 opcode/flags 样本与独立零字节FLUSH服务时间，在实际fdatasync对照中验证；但未捕获队列起点或不能建立请求生命周期时仍显示UNKNOWN，不用地址hash猜对象实例。240条逐设备I/O首次出现时的未知前值也不补零。这不影响已确认的CPU/文件事实，但不能宣称完整存储分账。

v8另外两轮、16个任务的真实搜索复验已通过输出与离线重建；每轮仍有queue unknown 3、untracked unknown 1，整体保留INCOMPLETE。这两轮与较早6轮诊断均不计入300轮正式性能/压力试验，不拿来推算slowdown。

本轮没有付费 API 调用。上一轮的小规模 SWE-bench Verified / AgentBench / Terminal-Bench 结果保留在 [命名 benchmark 记录](../agent-benchmarks/README.md)，没有冒充新跑的完整测试集成绩。
