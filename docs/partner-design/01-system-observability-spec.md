# 观测功能说明

这份文档说明：给 Agent 接上 Observer 后，用户能多看到什么。

以“Agent 修改代码并运行测试”为例，原来只能看到命令输出；接入后，还可以查看记录到的文件操作、子进程，以及检查范围内的前后状态变化。需要做恢复实验时，还能检查回滚后留下了什么。

这里讲的是功能和报告。具体接法见 [Allox + Observer 接入说明](02-code-mode-integration-contract.md)，虚拟机内外的部署位置见 [Kata 部署说明](03-codex-kata-architecture.md)。

## 1 谁负责执行 谁负责观察

| 组件 | 用一句话解释 |
|---|---|
| Allox | 给任务准备工作目录、运行命令，需要时恢复工作区文件 |
| Observer | 记录受支持的系统操作，比较执行前后的文件和系统配置 |
| Kata | 把执行环境放进虚拟机，增加与宿主机之间的隔离 |

Observer 不负责替 Agent 执行任务，也不负责把整个 Linux 恢复原样。它的作用是提供记录和检查结果。

## 2 一次任务结束后能看到什么

下面是一份建议展示给用户的报告示例，不是新的测试结果，也不是现成界面：

```text
任务：修改代码并运行测试
命令结果：成功

执行记录
  记录到 effect.txt 的创建和写入操作
  记录到测试进程的启动和退出

执行后的文件变化
  工作目录新增 effect.txt

本次检查范围
  已检查：指定工作目录
  未检查：BPF、系统配置、内核模块

恢复检查
  未开启，本次保留任务产生的文件
```

现有工具已经能产生底层记录和差分文件；把它们整理成这样的报告、查询页面和统计图，仍需要产品接入代码。

用户主要看三件事：任务做过什么、最后留下什么、这份记录是否完整。命令返回成功，不等于这些检查也全部成功。

## 3 可以检查哪些影响

各项检查需要单独启用，并指定检查范围；不是装上 Observer 就默认检查整台机器。

| 检查内容 | 用户可以看到什么 | 要注意什么 |
|---|---|---|
| 文件 | 选定的创建、写入、删除、重命名等操作；指定目录内的新增、删除和属性变化 | 文件内容是否相同，需要启用内容检查；不是全盘扫描 |
| 进程 | 记录到的进程创建、程序执行和退出；任务结束时指定进程组内还有哪些任务 | 已有记录不代表所有逃逸、迁移和异步执行都被完整覆盖 |
| 网络 | 选定连接操作及部分地址信息；本机地址、路由等配置变化 | 不能证明远端数据库或 API 的最终状态 |
| 系统配置 | 指定 sysctl 参数和挂载信息的前后变化 | sysctl 就是 Linux 的一组可调整系统参数，需要列出要检查的项目 |
| BPF 对象 | 内核中 BPF 程序、Map、Link 等对象的变化 | 对象和 Map 内容各有检查开关，内容类型并非全部支持 |
| 内核模块 | 已加载模块列表及选定可读参数的变化 | 列表相同不代表模块内部所有状态都相同 |

Observer 使用 eBPF 采集记录，但并不只观察 BPF 子系统。BPF 状态只是上表中的一个检查项目。

权限监测还在扩展：当前可看到部分权限相关调用，但完整的“拥有什么权限、权限如何变化、每次访问为什么允许或拒绝”尚未全部实现，不能作为已交付能力展示。

## 4 为什么既要记录操作 又要比较前后状态

假设 Agent 创建了 effect.txt，随后又删除它。

- 操作记录能说明：中间发生过创建和删除。
- 前后比较能说明：开始和结束时都没有这个文件。

两者不矛盾。只看最后的文件列表，会漏掉中间过程；只看写入操作，也不知道文件最后是否还存在。

如果机器上还有其他程序同时修改系统配置，前后差异也不一定全由这个 Agent 造成。报告应把“记录到该任务的直接操作”和“这段时间里系统发生的变化”分开显示。

## 5 需要回滚时怎样检查

普通任务只记录执行前和执行后，保留任务成果。只有明确开启恢复检查，才执行回滚并采集第三次状态：

```text
A 执行前 → Agent 运行 → B 执行后 → Allox 回滚文件 → C 恢复后
```

以新建 effect.txt 为例：

| 检查对象 | A 执行前 | B 执行后 | C 回滚后 |
|---|---|---|---|
| effect.txt | 不存在 | 存在 | 不存在 |

这个例子可以说明文件的新增已被撤销，但不能直接得出“整个系统都恢复了”。

再假设任务有权限修改一个已纳入检查的 sysctl 参数。Allox 回滚工作区文件后，这个参数可能仍保持新值。报告就应同时显示“文件已恢复”和“系统配置仍有差异”。

因此恢复报告分成三部分：

| 用户要知道的事 | 比较哪两次状态 |
|---|---|
| 执行期间改变了什么 | A 和 B |
| 恢复过程撤销或新增了什么 | B 和 C |
| 恢复后还有什么不同 | A 和 C |

Observer 的“状态记录”是所选文件和配置的检查结果；Allox 的“检查点”是用于恢复工作区文件的存档。它们都可能被叫作快照，但用途不同，也都不是完整虚拟机内存快照。

## 6 怎样理解恢复结论

| 报告结论 | 通俗解释 |
|---|---|
| 检查范围内恢复一致 | 记录完整，并满足该范围的比较条件，未发现恢复残留 |
| 检查范围内恢复不一致 | 记录完整，并发现恢复后的确定差异 |
| 暂时无法下完整结论 | 有检查未完成、记录缺失或其他条件不满足 |

“暂时无法下完整结论”不等于“什么都没看到”。例如文件检查发现了残留，而另一个检查项目失败，报告仍要列出已经确定的文件差异。

当前还有两类容易误解的情况：

- 报告复核通过，只表示能够根据原始记录重新算出报告，不表示恢复一定成功。
- Allox 恢复文件时，会从存档生成一个新的工作目录来替换旧目录。文件内容可以相同，但底层目录标识、时间等仍可能不同。当前比较器保留这些差异，所以文件内容恢复后，总结论仍可能不是“恢复一致”。

BPF 严格无变化判断等条件也尚未全部接入当前恢复流程。不能为了显示成功，把这些限制隐藏起来。

## 7 怎样知道 Observer 有没有漏记

报告除了列出变化，还应说明记录质量：

- 没启用某项检查，显示“未检查”。
- 事件来不及保存而丢失，显示“操作记录不完整”。
- 知道发生了写入，但没解析出目标文件，显示“目标对象未知”。
- 文件扫描失败或配置读取失败，显示具体失败范围。
- 原始记录缺失、被改动或无法复算，显示“报告复核失败”。

这些情况不能当成“没有发生修改”，也不能直接叫作“Agent 攻击”。普通的权限拒绝同样不自动等于恶意越权。

记录应保存在 Agent 不能修改、文件回滚不会删除的位置。若被观测的 Linux 内核已经被攻破，来自该内核的记录也不能继续被当作完全可信。

## 8 开启观测会不会变慢

会增加开销，主要来自两部分：

- 任务运行时记录事件。
- 任务开始、结束和恢复后，检查文件及系统配置。

当前已有减少开销的做法：只记录选定任务和操作、限制事件大小、把状态检查放在阶段边界。检查目录越大、内容检查越多，耗时也可能越高。

性能报告应直接回答“任务多用了多少时间、Observer 多用了多少 CPU 和内存、记录有没有丢失”，而不是只给一个快照耗时。

测量时在相同环境下反复运行相同任务，比较开启与关闭 Observer 的结果。Kata 本身的开销需要另算；不能把换成虚拟机之后增加的全部时间都算给 Observer。现有历史边界耗时不代表新环境的性能保证。

## 9 第一版产品先做到什么

先接一个命令工具，指定一个工作目录，完成以下验收即可形成最小可用版本：

1. 创建 effect.txt，报告里能看到相关操作和新增文件。
2. 再做一次专门的恢复实验，能看到文件被删除以及实际恢复结论。
3. 某项检查失败时，报告明确显示失败，不伪装成没有变化。
4. 同一任务重复运行，给出开启与关闭 Observer 的耗时对照。

Allox + Observer 已有直接执行的接入基础；产品报告页面、完整权限监测和 Kata 联合接入仍是后续工作。

## 附录 工程实现时查阅

正文中的“检查范围”在配置里称为 scope，表示检查哪些目录、配置或对象；“记录策略”称为 profile，表示运行时记录哪些操作。两者需要分别设置。

当前 profile 为 control、balanced、full。control 不包含普通 write 数据路径；需要验证写入事件时应选择包含该操作的策略。full 也不代表覆盖全部 Linux 行为。

产品统计可先实现下面几项。指标名称是建议，不是已有监控接口：

| 建议指标 | 展示内容 | 计数要求 |
|---|---|---|
| agent_observer_runs_total | 完成了多少次执行 | 每次实际执行结束计一次 |
| agent_observer_run_duration_seconds | 任务运行多久 | 与准备、快照和报告复核时间分开 |
| agent_observer_operations_total | 记录到多少次操作 | 不把同一调用的进入和返回算成两次 |
| agent_observer_events_lost_total | 丢失了多少条记录 | 区分采集、队列和落盘来源 |
| agent_observer_snapshot_duration_seconds | 各项状态检查用了多久 | 按阶段和检查项目区分，保留失败情况 |
| agent_observer_recoveries_total | 各类恢复结论出现多少次 | 每份最终恢复报告计一次 |

每份报告需绑定执行编号、目标 Linux 身份和检查范围，避免把不同任务或重启前后的记录混在一起。任务编号和文件路径用于查询，不默认作为每条统计曲线的标签。

底层恢复结论分别为 `CONSISTENT_WITHIN_SCOPE`、`INCONSISTENT_WITHIN_SCOPE`、`INCONCLUSIVE`。任一启用项目不完整可能使总结论成为 `INCONCLUSIVE`，但已确定的差异仍需保留。

详细能力、对象解析缺口、状态域和证据规则见 [Observer 现有规格](../specification.zh-CN.md)。实际接入接口和结果路径见 [Allox + Observer 接入说明](02-code-mode-integration-contract.md)。
